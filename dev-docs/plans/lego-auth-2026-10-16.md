# RFC — LEGO auth-better-auth

**16 octubre 2026 · PR futura `feat/lego-auth` desde `main@5920396bdba391d66caf7b36e4f15dec56fa3f41`.**
**Clasificación:** add-on experimental, opt-in, sin publicación ni producción.

## Fuentes y decisiones

- Documentación oficial: https://better-auth.com/docs/integrations/fastify, https://better-auth.com/docs/adapters/drizzle, https://better-auth.com/docs/concepts/session-management, https://better-auth.com/docs/concepts/rate-limit, https://better-auth.com/docs/plugins/admin.
- Evidencia previa: `dev-docs/validation/2026-10-14-gh-actions/report.md` (rama de investigación `feat/fastify-lego-foundation`), pruebas Better Auth 1.7.7, PostgreSQL real, signup/login/logout/session.
- Mejorar esa evidencia con **Better Auth y adapter 1.7.10**, último parche estable indicado por documentación en la fecha, Drizzle ORM 0.45.4, Drizzle Kit 0.31.11 y pg 8.23.1, Node 24 / pnpm 11.25.
- Separar `addons/auth-better-auth` de `addons/db-postgres`, `examples/identity-access` y de las plantillas Fastify. El Core sigue sin sesiones ni conexiones obligatorias. **PostgreSQL es prerrequisito de servicio**, no una importación global.
- Las tablas Better Auth viven en esquema `auth` y se migran solo por comando explícito en un **journal exclusivo `auth_meta.__drizzle_migrations`**. El ejemplo `lego_app.notes` conserva su migrador independiente `drizzle.__drizzle_migrations`: nunca tener dos dueños de una tabla ni mezclar sus journals.
- El add-on recibe DSN de rol DML no dueño de esquema, baseURL fija, secreto >=32, trusted origins exactos. Se impide HTTP no-loopback, wildcard CORS, uso de Host header como autoridad y alteración de roles desde signup. No activar el plugin `admin`: no hay mutación admin, y `role` es campo interno con `input:false` y default `user`.
- Better Auth posee sesión cookie HTTP-only, sin cookieCache y con acceso real a PostgreSQL para invalidación tras signout. `getPrincipal()` resuelve sesión en DB; **cada ruta de negocio debe comprobar autorización por recurso**. Ejemplos de 401/403 en tests, no presentar RBAC/multitenancy genéricos.
- `@fastify/cors` deliberadamente **ausente**: ejemplo solo mismo origen; cross-origin será pieza futura aislada y con orígenes restrictivos. Rate limiting en memoria solo para test, **no distribuible como protección de múltiples nodos**.
- Fallos de esquema/conexión antes de escuchar: abortar de forma segura; `onClose` libera pool. No logs de password, cookie, secret, SQL ni DSN. No migraciones automáticas al iniciar.

## Gates

A: versiones y lock propios, scripts de instalación sin efectos secundarios y checkout sin token; `pnpm audit --prod`, full audit. B: schema generado por CLI/Drizzle versionado, `drizzle-kit check`, migración repetida con **un registro en `auth_meta`**, distinto del historial `drizzle` del addon DB. C: roles PostgreSQL diferenciados: migrador vs runtime DML sin DDL, sin acceso `lego_app`/journals. D: E2E auth real signup/login/session/logout, cookies, anti-admin signup, usuarios distintos 401/403 y origen ajeno. E: Fastify Core puede arrancar sin credenciales ni DB; auth opt-in se compone con el Core compilado en directorio distinto. F: pruebas negativas por URI/secret/origen inválidos, redacción de errores, cierre del pool. G: CodeRabbit, fixes mínimos y CI final green.

**NO-GO producción:** backups/restore, origen TLS detrás de proxy, CSRF/cookies reales de navegador y cross-domain, rate limiting centralizado, múltiples instancias, tenant authorization y rotación de secretos fuera de este laboratorio. Mantener explícito el waiver de 70 errores de `.d.ts` upstream Drizzle 0.45.4 bajo `skipLibCheck:false`, sin presentarlo como typecheck completo. No hay migración automática desde el ejemplo Identity Access heredado ni bootstrap de administradores.
